# Backend integration: router mounting, API client, and page rewrites

This PR wires 11 frontend page components to the FastAPI backend by introducing a centralized API client (`lib/api.ts`), mounting the previously-disconnected `communities`, `claims`, and `messages` routers in `main.py`, and adding a database seed script for development. Each page now fetches real data through typed helper functions instead of importing from `mockData.ts`. The auth integration uses `AuthContext` to hydrate the user from a stored JWT on load and attaches the token to every request via a shared `apiFetch` utility.

Watch for: the Messages inbox page was gutted to a static empty-state placeholder rather than connected to the backend (confirmed); the `BrowseListings` useEffect has a missing dependency that can cause stale closures (confirmed); the `ListingDetails` and `Dashboard` pages issue unauthenticated-looking requests to auth-required endpoints without handling 401s gracefully (likely); and the seed script has a circular FK insertion order that will fail on a fresh database with referential integrity enabled (confirmed).

## High-level view

The API client is well-structured: a single `apiFetch` generic handles token injection, JSON parsing, error mapping, and 204 responses. Type interfaces mirror the Pydantic response schemas faithfully, and HTTP methods match the backend routers (notably `PATCH` for listing updates).

The seed script inserts `MessageThread` rows before the `ClaimRequest` rows they reference via `claim_request_id`. Since the `message_threads.claim_request_id` column has a foreign key constraint to `claim_requests.request_id`, this insertion order will fail on a database with immediate referential integrity enforcement.

The Messages inbox page was entirely replaced with a static `EmptyState` component, dropping the previous conversation list, search, and unread counts. There is no backend endpoint that returns "all threads for a user," so the page can't be connected yet, but this is a functional regression visible to users during development.

Data-fetching error handling is inconsistent: most pages surface errors with a retry-able `EmptyState`, but Dashboard silently swallows all failures and MessageThread silently drops send errors.

## Seed script insertion ordering

The seed script flushes `MessageThread` rows (with `claim_request_id=1,2,3`) before the `ClaimRequest` rows that define those IDs. On a standard PostgreSQL database with immediate FK enforcement, this will raise an integrity error.

The fix is to insert `ClaimRequest` rows first (without `message_thread_id`), flush, then insert `MessageThread` rows, flush, then update the claims' `message_thread_id` fields. This mirrors the pattern used in the `create_claim` endpoint itself.

## Messages inbox regression

The previous `Messages.tsx` rendered a conversation list sourced from `getThreadsForUser()` mock data, including search filtering, active/older groupings, and unread indicators. The new version is a static page that tells users to go browse listings. The `MessageThread` page still works (it uses `GET /v1/claims/{claim_id}/thread`), but there's no way to discover which threads exist without already knowing a claim ID.

The backend doesn't expose a "list all threads for user" endpoint, so full restoration isn't possible without a new backend route. The gap should be documented or a minimal solution added (e.g., fetching the user's claims and rendering their thread references).

## BrowseListings effect dependency

```tsx
useEffect(() => {
  loadListings();
}, [searchQuery, activeCategory]);
```

`loadListings` is declared as a plain function in the component body. React's exhaustive-deps rule would flag this. It isn't a runtime bug today because the effect re-runs when the listed deps change, but it's fragile if the function gains additional closure dependencies later (e.g., a community filter that doesn't trigger the effect).

## Dashboard and error handling asymmetry

Dashboard wraps the entire `Promise.all` in a bare `catch {}` block with no error state, no retry button, and no user feedback. If the token is expired or the server is down, the user sees an empty dashboard with no indication that something went wrong.

The `MessageThread` page has a similar issue for the send action: the catch block is empty, so if sending fails (network error, 403, etc.), the user's message silently disappears without feedback.

## Authentication boundary gaps

`ListingDetails` calls `getClaimsForListing` unconditionally after loading a listing. That endpoint requires a valid token (`get_current_user` dependency). If an unauthenticated user views a listing detail page, this call returns a 401 which gets caught by `.catch(() => setClaims([]))` — fail-silent. The claim submission form will also fail at 401 for anonymous users, surfacing "Could not validate credentials" as the error message, which isn't user-friendly.

The `browseListings` endpoint has no auth requirement, so anonymous browsing works. But pages like `ListingDetails` and `Dashboard` that call both authenticated and unauthenticated endpoints in the same load need to handle the auth split deliberately — either gate the auth-required calls behind `if (user)` or redirect to login on 401.

## Profile reviews section

The reviews section now renders a permanent `EmptyState` instead of calling the `GET /v1/users/{id}/reviews` endpoint from the API spec. The reviews backend router doesn't exist in this diff, so this is a deliberate placeholder — but it should include a TODO comment making the gap explicit.
